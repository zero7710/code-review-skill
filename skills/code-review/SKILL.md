# 代码审查与讲解

先判断用户要决定什么。问“这次改动会不会出错”，走审查入口。问“现有代码为什么这样工作”，直接走讲解入口。两件事都要时，分别给出解释和审查证据。只有明确要评测审查器时，才读取[历史案例评测](references/evaluation.md)。

## 确定源码与规则

- 从**被审查的仓库**读取适用的 `AGENTS.md`、项目维护的 `REVIEW.md`（如有）和任务明确给出的约定。对 PR，把改动意图与目标分支已采用的规则交给审查者，PR 提议的规则变更也要接受审查。仓库未提供审查规则时，仍可依据调用方、测试和既有契约判断代码行为。涉及谁批准、谁发起合并时，以该项目可核实的规则为准。
- 记录实际审查的版本。PR 从目标分支与待审提交的共同祖先定位完整差异。第 3 轮比较最近一次已完成审查的提交到当前提交。审工作区时覆盖暂存、未暂存和任务相关的新文件，注明工作区状态。指定提交的讲解读取该提交的源码。只有核对过的干净文件才能用提交及行号作永久定位。
- 正常使用以当前任务输入为范围。盲测时把当时可见的源码、规则、验证材料传给全新审查上下文。判分答案、事故、后续修复及调优记录只给评分方。

## 审查一次改动

按[审查与复查](references/review.md)实际分派独立的发现和复核任务。先定位差异及其影响路径，再用触发条件、错误后果和代码证据裁定候选问题。已有意见沿用输入的原编号。没有独立复核、缺少上一轮基准或覆盖不完整时，报告具体缺口。发现、安全审查、CI、人工审批和合并门禁分别取证。

默认交付可执行的审查意见。用户同时要求修复时，在授权范围内修复并用同一触发条件验证。发布 PR 评论、上报外部服务、批准和合并分别遵循用户对相应操作的授权。没有线上连接时，本地审查与交接仍可完成。

## 讲清一段代码

1. 把问题收窄到一项可观察行为。从实际入口追踪到产生结果的条件、读写和下游消费者。核实正在使用的模块，记录仓库相对路径、符号、行号及版本。
2. 先用一句话回答，再给出最短的证据路径。区分源码可证实的行为、文档中的意图和仍待确认的设计原因。在有关键分支或跨模块传递时绘制简短调用图或数据流图，每个业务节点能回到对应源码。
3. 供分享的讲解保留原问题、源码版本和所选节点。本入口不需要 PR。发现值得进一步审查的疑点时说明它对应哪个问题，按用户任务决定是否转入审查。

## 交付给人和运行程序

审查汇总从已核实的问题数开始，给出影响最大的发现、覆盖缺口和下一位处理人。讲解从问题的答案开始。两种入口均按[结果交接约定](references/outputs.md)整理结果。交互使用时给出可读结论及结构化结果。运行程序或用户指定 JSON 时，直接返回符合[结果 Schema](references/result.schema.json)的单个 JSON 对象。调用方指定文件时写到该文件。接入项目后台时，运行程序负责记录所用 Skill 版本、保存结果、上报重试和同步代码平台状态。
